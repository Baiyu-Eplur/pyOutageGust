# Step 3：过滤/合并/筛选方案建议（只提方案，不执行）

以下六条建议均基于 Step 0-2 的实测数字，每条给出理由，不只给结论。

## 1. Cause Code 筛选

**建议：正式分析阶段保留全部事件，不在数据构建层筛选；Cause Code 分组作为分析时的可选参数（已有 `cause_group_official` 列可直接用于筛选）。**

理由：
- 取消预筛选后，weather_natural+technical_asset 合计 66,078 个事件（48.9%），与旧 v6 口径的 62,928 个量级接近但不完全相等，说明"只保留这两组"本身是一个可复现的合理默认选项，但**不是唯一选项**。
- non_fault_or_unknown 组占比高达 39.4%（53,148个事件，绝大部分是 Cause Code 97 "No Fault Found"），third_party（7.6%）、human_error（0.5%）、external_or_customer（3.7%）合计还有约11.8%——这些类别此前从未被纳入过阵风效应分析，取消预筛选后的数据集第一次让"扩大 Cause Code 范围是否改变阵风系数的稳健性判定"这个问题变得可测（呼应工作命令#4/#5发现的"小样本下效应不稳健、大样本下部分复现"模式，样本量本身可能是关键变量）。
- 如果在构建数据层就直接筛掉，后续任何"对照不同 Cause Code 范围"的分析都要重新构建数据；保留全量、下游按需筛选，一次重建可支持多组对照分析，工程成本更低。

## 2. customers=0 / "No Fault Found"类记录处理

**建议：不排除，但需要新增一个显式布尔标记列（如 `is_zero_customer_event`），供下游模型按需处理，不要求下游必须处理。**

理由：
- customers_v2=0 的事件有12,648个（约9.37%），且这批事件正是导致 duration_A 无法计算的主要原因（见Step2第4节）——它们不是"脏数据"，而是官方口径下真实存在、影响规模为0的记录（此前主线审计也发现这15%量级的现象，本次口径下比例接近但因排除了重复中断阶段口径变化后略有不同，仍是同一现象）。
- 直接排除会系统性丢失一大类真实事件，且这批事件在多个下游模型中（尤其是以customers为自变量取对数的模型）本身就需要特殊处理（如log1p变换、或作为单独示性变量），排除不能替代妥善的建模处理。
- 保留+标记，把"是否纳入"的决定权留给具体分析（例如暴露侧回归可能需要排除或用示性变量处理，但恢复侧/duration_B为因变量的模型完全可以正常纳入这些事件）。

## 3. 10.56%"疑似缺失起始阶段"事件的处理

**建议：默认保留并直接使用，但同步新增一个显式标记列（如 `suspected_missing_first_stage`），用于后续必做的敏感性分析（对比"含 vs 剔除"两个版本的关键回归系数是否稳健）。不建议现在就排除。**

理由：
- 14,264个事件（10.56%）占比不小，直接排除会损失可观样本量，而且命令背景已说明这一现象"均匀分布在整个研究期内，不是时间窗口边界效应"，即没有证据表明这是某种可清楚界定的数据错误，更可能是官方记录本身存在阶段编号不连续的常见现象（如首个阶段未单独生成 Restoration Stage 记录）。
- 但这批事件的 customers/duration 很可能被系统性低估（因为观测到的"最早阶段"其实不是真正最早的阶段，跨阶段聚合会漏算真正的起始阶段），如果不做标记，无法在后续分析中检验这一潜在偏差对结论的影响。
- 标记+保留优于直接排除或直接忽略：既不牺牲样本量，也为方法论稳健性检验留了接口。

## 4. 69个边界情况事件（全阶段皆重复中断）的处理

**建议：为 customers/暴露侧分析排除这69个事件（customers_v2 天然为 NaN，无法通过现有信息合理插补）；为 duration/恢复侧分析保留（duration_B 对全部69个事件均可计算，duration_A 对其中的大多数也可计算，因为其分母使用的是全部阶段客户数而非排除重复中断后的客户数，与Step1发现的实现细节相关）。不建议为这69个事件专门设计客户数估算规则。**

理由：
- customers_v2 的定义就是"排除重复中断阶段后求和"，如果全部阶段都是重复中断，该定义在逻辑上就没有可计算的结果，属于定义域边界，不是数据缺陷，用其他口径（如"改用全部阶段客户数之和，不排除重复中断"）去强行填补，会破坏该变量原本"剔除重复计数"的设计初衷，且只影响69/135,025=0.05%的事件，样本量损失可忽略。
- duration 两个口径都不依赖 customers_v2，可以正常保留，让暴露侧和恢复侧模型对这69个事件采用不同处理方式（暴露侧剔除、恢复侧保留）在方法论上是自洽的，不是"双重标准"。

## 5. 下游天气匹配/LAD合并的重跑范围评估

**结论先行：新增的72,097个事件里，81.0%（58,386个）已经在现有天气缓存里命中，只有11.2%（8,100个）需要新发起API请求，另有7.8%（5,611个）是坐标/时间本身无效、发新请求也无法解决。工作量比预想的小很多。**

**建议：现阶段就可以为这8,100个事件发起新的天气API请求补齐缓存，不需要等到customers/duration方法论完全确定之后再做**，可与后续验证性分析并行推进；同时，即使不补齐这8,100个，当前已有121,313个事件（89.85%）天气特征齐全，样本量已经是旧口径62,928的约1.93倍，完全可以先用这批已匹配数据做customers/duration本身的验证性分析（不阻塞天气API请求的完成）。

理由：
- 旧口径的62,928个事件在新数据集中几乎100%命中缓存（62,927/62,928），说明缓存本身覆盖良好，本次重建复用现有缓存的策略是合理的，不需要为已有事件重新发起请求。
- 8,100个待补齐请求相对于总量（135,025）只占6.0%，属于可控的小规模增量工作，不构成需要延迟整体分析的理由。
- invalid_time_or_coordinate 的5,611个事件是数据本身（原始坐标或时间字段无效/超出英国范围）的问题，重新请求API无法修复，需要单独在数据质量层面处理（如缺失空间坐标的补全或干脆标记为不可用于天气相关分析）。

## 6. duration_A vs duration_B 选择的量化基础

**不下结论选哪个，仅提供量化差异供后续决定：**

- 单阶段事件（93,944个，69.4%）：duration_A 恒等于 duration_B（差异100%为0），两口径在此类事件上没有区别。
- 多阶段事件（41,081个，30.6%）：两口径差异显著——
  - 相对差异中位数 **54.3%**，说明典型情况下两个口径给出的时长相差超过一半
  - **84.0%的多阶段事件相对差异超过10%**
  - **68.7%的多阶段事件绝对差异超过1小时**
  - 差异方向：duration_B（事件总跨度）均值11.99小时 > duration_A（客户数加权）均值5.84小时，说明duration_B系统性地大于duration_A（符合逻辑：total span 天然涵盖所有阶段的时间总长，而加权平均会被客户数较少、耗时较短的阶段"拉低"）。
- **覆盖率差异是一个不能忽略的实际因素**：duration_A 有9.37%（12,650个事件）缺失，且缺失高度集中在customers=0/No Fault Found一类事件（Step2第4节已定位）；duration_B 无缺失，135,025个事件全部可计算。
- 供后续决策参考的问题清单：①如果研究问题关心的是"典型客户经历的平均停电时长"，duration_A的加权设计更贴切，但需要先解决9.37%缺失值的处理方式（插补 或 该子集单独用duration_B替代）；②如果研究问题关心的是"整个抢修事件从发现到完全恢复的总耗时"，duration_B的定义更直接，且无缺失问题；③Step1发现的"duration_A分母未排除重复中断阶段客户数"这一实现细节，如果后续选择duration_A作为主口径，需要网页端先确认这是否是有意设计（如果不是，需要先修正再使用）。

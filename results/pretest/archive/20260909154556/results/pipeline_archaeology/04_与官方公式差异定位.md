## 官方口径（转述）vs. 现有代码逐条对照

### 官方口径 1：customers 需要跨 Restoration Stage 求和（或至少正确聚合多阶段记录）

**现有代码具体怎么做**：`filter.py` 中（详见 `03_脚本详细文档.md` 已摘录代码）：

```python
df_filtered = df_filtered.sort_values([incident_col, "_sort_time"], kind="stable")
df_unique = df_filtered.drop_duplicates(subset=[incident_col], keep="first").copy()
```

按 `Incident Reference` 分组，排序后只保留时间最早的**一条** Restoration Stage 记录，其余所有阶段记录（含所有 Re-interruption Stage 记录）在这一步被**整体丢弃**，之后的 `main1.py`/`match_lad.py`/…/`data_arrange.py` 全部基于这唯一幸存的一行做后续处理，从未回读被丢弃的其他阶段行。

`Number of Customers Restored` 字段本身在幸存的这一行里，从 `filter.py` 到 `data_arrange.py` 全程**没有被任何脚本重新赋值、聚合或重算过**（`03_脚本详细文档.md` 末尾"跨脚本追溯结论"一节已用全库 grep 核实：全部 12 个主链+子链脚本中，唯一出现 "Customer" 关键字的是 `deeprig.py` 第101行 `df["customers_restored"] = safe_num(df["Number of Customers Restored"])`，且这只是类型转换，不属于九步主链，也不涉及跨阶段聚合）。

**与官方口径的具体差异**：**不是"求和方式不对"，而是"根本没有发生跨阶段求和这个动作"**——因为其余阶段的记录在最初一步就已经被物理删除，连"错误地求和"的机会都没有。当前 customers 值 = 该 incident 最早一条 Restoration Stage 记录里原始 `Number of Customers Restored` 字段的原样透传，等价于"只统计第一次抢修阶段汇报的客户数"，既不是官方要求的跨阶段总和，也不是任何形式的去重后总和。

### 官方口径 2：customers 需要排除重复中断（duplicate/re-interruption 记录去重计数）

**现有代码具体怎么做**：由于官方口径 1 描述的原因（其余阶段行已被丢弃），`filter.py` 及后续脚本中**不存在任何针对 Re-interruption Stage 的显式去重/标记逻辑**——`filter.py` 全文（`03_脚本详细文档.md` 已逐行核实）没有引用 `Re-interruption Stage` 字段，`classify_cause_code()`/`generate_weather_fetch_list_strict()` 两个核心函数均只操作 Cause Code 相关字段，不触碰 Restoration/Re-interruption Stage 标记字段。

**与官方口径的具体差异**：这一条差异是**官方口径1差异的直接推论**——因为多阶段记录本身已被整体丢弃，"是否正确区分/排除重复中断"这个问题在当前代码里是**不适用（moot）**的，而不是"处理了但处理错了"。换句话说，现有代码既没有做对，也没有做错，而是从一开始就没有面对这个问题——它绕过了这个问题（通过丢弃数据）。这与 codex 独立审计的 `audit_reinterruption_stage` 报告一致：该报告确认原始文件 237,901 行对约 62,928-66,080 个唯一 incident（约3.6 阶段/incident），Reinterruption 字段 Y/N 分布约 91.3%/8.6%，且明确引用 Ofgem ED1 Annex F 2020 para 2.59（第27页）说明官方要求对同一 Restoration Stage 内的多次 clock-stop 按 Reinterruption=Y 标记处理——这套官方规则在当前用户代码里完全没有被实现或引用。

### 官方口径 3：duration 需要按客户数加权，且包含重复中断的影响

**现有代码具体怎么做**：`data_arrange.py`（`03_脚本详细文档.md` 已全文摘录）：

```python
duration = (df[end_col] - df[start_col]).dt.total_seconds() / 3600
duration[duration < 0] = pd.NA
```

`Duration (hours)` = 单一幸存记录的 `End Date and Time` 减去 `Start Date and Time`，直接转换为小时数，是一个**纯粹的单阶段时间差计算**，不涉及任何客户数加权（没有乘以/除以任何 customers 相关字段），也不涉及跨阶段的时间累加或客户数分段加权平均。

**与官方口径的具体差异**：**没有任何客户数加权步骤，也没有任何跨阶段时长累计**。当前 duration 值等价于"该 incident 最早一条 Restoration Stage 记录自身的起止时间差"，如果该 incident 实际经历了多个 Restoration Stage（例如先临时恢复部分区域供电、再彻底修复），当前代码只捕捉了最早那一条记录的时间跨度，其余阶段（可能是耗时更长的最终修复阶段，也可能是更短的临时恢复阶段）的起止时间完全没有进入计算——是否被低估或高估取决于"最早的一条记录"具体对应哪个阶段，这一点本命令未能进一步细分（需要访问原始多阶段数据才能量化，见下方"影响幅度"讨论）。

## 差异定位小结表

| 官方口径要求 | 现有代码状态 | 差异性质 |
|---|---|---|
| customers 跨 Restoration Stage 求和 | 完全没有发生（阶段行已被 `filter.py` 丢弃） | 缺失整个聚合环节，非"聚合错误" |
| customers 排除重复中断计数 | 不适用（moot，多阶段数据已不存在） | 问题被绕过而非处理错误 |
| duration 按客户数加权、含重复中断 | 单阶段起止时间差，无加权 | 缺失加权环节，且只反映单一阶段的时长 |

**根本原因归一**：以上三条差异全部可以追溯到同一个代码位置——`filter.py` 中的 `df_filtered.drop_duplicates(subset=[incident_col], keep="first")` 这一行。这一行在整条九步链路的**第一步**就把每个 incident 的多条 Restoration Stage 记录压缩成一条，导致customers 和 duration 两个变量后续在整条链路中都只能是"单阶段透传"，而不可能实现官方要求的跨阶段聚合。

## 如果要改成官方口径，理论上需要改动的范围

### 需要修改的核心位置

1. **`filter.py` 的 dedup 逻辑（`generate_weather_fetch_list_strict()` 函数内的 `drop_duplicates` 调用）**——这是**唯一必须修改的起点**。当前逻辑"分组后只保留最早一条"必须改为"分组后保留全部阶段记录 并新增一个聚合步骤"：
   - customers：需要新增按官方去重规则（区分 Restoration Stage 与 Re-interruption Stage，依据 Ofgem para 2.59 的标记规则）计算"去重后的受影响客户数"的聚合函数，可能需要引入 `Re-interruption Stage` 字段（目前完全未被读取）。
   - duration：需要新增"取该 incident 全部阶段中最早 Start 到最晚 End 的时间跨度"或"按官方 CMLt 定义分阶段计算客户数加权时长后再合计"的聚合函数——具体取哪种要看 Q1-Q5 文档里官方公式的精确数学定义（本命令因缺失该文件无法给出唯一答案，这是需要网页端/用户确认的开放问题）。

2. **`data_arrange.py` 的 duration 计算公式**——需要从当前的"单行起止时间差"改为"读取 `filter.py` 新聚合出的多阶段汇总时长字段"，公式本身（`(end-start)/3600` 转小时的思路）可以保留，但输入的 `start_col`/`end_col` 需要替换成聚合后的字段，或者直接读取 `filter.py` 已经算好的聚合 duration 列（更推荐后者，让 `data_arrange.py` 只负责"从聚合结果里派生 Hour/Month/Weekday/Daytime Indicator" 这类周边时间变量，不再重复做 Duration 主计算）。

### 改动规模判断

**不是"改一个聚合函数"这么小的改动，也不是"整个数据读取结构"那么大的改动，属于中间偏大的规模**，具体理由：

- **不属于"只改一个聚合函数"级别的小改动**，因为当前 `filter.py` 的 dedup 步骤发生在**最开始**，其后 `main1.py`（天气匹配）、`match_lad.py`（LAD 空间连接）等所有下游脚本都是基于"每个 incident 只有一行"这个假设设计和验证过的（例如 `main1.py` 的坐标/时间解析逻辑、`match_lad.py` 的空间连接，都隐含假设输入是"事件级"一行一条）。如果在 `filter.py` 里保留多阶段行而不做聚合，下游所有脚本都会因为行数暴增（约237,901行级别而非62,928级别）而产生错误的天气匹配、错误的 LAD 计数等连锁问题。
- **也不属于"整个数据读取结构都要重写"级别的大改动**，因为：
  - 需要重新设计聚合逻辑的范围**局限在 customers 和 duration 两个变量本身**，其余全部 361 列下游特征（天气、LAD、人口、剥夺指数、GVA、地理/DNO）都是基于事件的时间/坐标/LAD归属计算的，这些字段的计算逻辑与 customers/duration 是如何被压缩到单行无关，**不需要修改**。
  - 具体实现方式可以是：在 `filter.py` 的 dedup 之前，先按 incident 分组计算出"聚合后的 customers 值"和"聚合后的 duration 起止时间"两个新字段，附加到保留的那一条记录上，然后 dedup 逻辑本身（保留哪一条作为代表行）基本不变——即：**改动集中在 dedup 之前插入一个新的聚合步骤，而不是重写整个 filter.py 或推倒重来**。
- 需要额外确认的技术前提：目前原始 `data/ukpn-iis.csv`（44MB）在本次沙箱环境中两次尝试传输均失败，本命令没有拿到原始多阶段记录做实际验证性试算；若网页端/用户后续要实施这一修改，第一步应先解决"如何在本地环境（而非本次云端沙箱）里正确读取原始多阶段数据"这一操作性问题，然后再决定聚合函数的具体实现细节。

### 因缺失 Q1-Q5 文档而无法确定的开放问题（明确列出，待补充）

1. 官方 CMLt 的"按客户数加权"具体权重口径是什么（每个阶段各自的客户数？还是全 incident 唯一客户数？）——直接决定 duration 聚合公式的精确形式。
2. 官方对"重复中断"的排除规则是否只影响 customers 计数，还是也会影响 duration 计算范围（例如某些 Reinterruption=Y 的阶段是否应被计入总时长）。
3. Ofgem 官方口径是否要求"跨 Restoration Stage 求和"这个说法对应的是**customers 求和**（不同阶段影响的客户可能不完全重叠，是否需要去重后求并集）还是仅仅是**duration 的跨阶段拼接**——命令原文的措辞"跨 Restoration Stage 求和"更像是在描述 customers，但"customers 排除重复中断"这半句又表明 customers 本身不是简单求和而是去重计数，这两句放在一起在语义上需要 Q1-Q5 原文的精确表述才能消除歧义。

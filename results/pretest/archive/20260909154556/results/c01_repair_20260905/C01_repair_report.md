## 0. Bug确认：代表行选取的实际代码位置

`code_audit_20260905`审查指出的问题已在代码中精确定位并确认属实：

**`claude_branch/scripts/v3_validation/v3_validation_pipeline.py`第61-64行**：
```python
def step0_build_sample():
    df = pd.read_csv(SRC, usecols=USECOLS, low_memory=False)
    event = df.drop_duplicates(INCIDENT_COL).copy()   # keep="first"默认值，按文件行序
```

`df.drop_duplicates(INCIDENT_COL)`默认`keep="first"`，保留的是**该事件在CSV文件中最先出现的那一行**，不是按开始时间排序后的最早阶段。这个函数是`step0_build_sample()`，被本项目全部下游脚本（`clean_sample_builder.py`、`build_holdout_sample.py`、进而`combined_sample_builder.py`）间接调用，即命令#16、#19、#21乃至此后几乎全部命令使用的事件级样本，均继承了这一选取规则。

抽样核实还发现：原始`ukpn-iis.csv`（对应v3文件的`source_row_number`顺序）本身**不是按Incident Reference分组、也不是按时间排序的**——同一事件的多条阶段记录可能分散在文件的任意位置（例如事件`FREP-231661-Z`的13条阶段记录分散在source_row 1到237,716之间，几乎横跨整个文件），这正是该bug会产生系统性影响而非随机噪声的原因。

## Step 5：综合判断

### 1. "二次项主导、二次项显著且稳健"这一核心发现是否依然成立？

**明确成立，未受影响。** 修复前后，E0二次项从0.1028增至0.1060（+3.1%），R0c二次项从0.0792增至0.0850（+7.2%），两者在5折交叉验证中均保持**5/5折同号、5/5折显著**，且折间CV%（衡量稳定性的指标）修复后反而**更低**（E0从15.83%降到13.19%，R0c从23.74%降到20.42%）——**修复后核心非线性发现不但没有减弱，稳健性指标上还略有改善。**

### 2. 暴露侧临界风速的变化幅度？是否依然落在观测范围内、通过两种置信区间检验？

**变化幅度很小：从10.694 m/s变为10.807 m/s，绝对变化+0.11 m/s，相对变化约+1.06%。** 阵风均值/标准差修复前后几乎不变（9.872/5.223 vs 9.910/5.280），临界风速z-score本身的变化（0.157→0.170）同样是小幅度的，可以合理预期修复后的临界风速依然落在观测分布的中高百分位区间内（与修复前63.7百分位量级相近，本命令未重新精确计算修复后样本的百分位数字，如实说明这一点未做，但基于z-score偏移幅度很小，判断结论不会发生实质变化）。**两种置信区间的定性结论完全保持不变**：Delta method 95% CI（[10.13,11.48]，不跨零）、Bootstrap 95% CI（z尺度[-0.143,0.426]，仍然跨零；物理单位[9.16,12.16]，仍是一个跨越约3 m/s的合理宽度区间）——与修复前的定性结论（"Delta不跨零、Bootstrap跨零，反映比值型统计量的抽样不确定性"）完全一致。

### 3. "阵风解释力有限、affected customers解释力更大"这一排序是否依然成立？

**排序依然成立，但阵风的相对权重有所上升。** 修复后customers_v2/阵风权重比从12.7倍降至7.4倍（阵风边际贡献从0.62pp升至1.06pp，增幅约71%；customers边际贡献从7.87pp降至7.80pp，基本持平）——**customers_v2依然是远比阵风更强的解释变量（7.4倍权重差），排序未改变，但差距有所收窄，是修复后一个值得在论文中如实反映的定量变化，不应笼统地说"没有变化"。**

### 4. 变化的方向和可能原因（描述现象，不做因果解释）

如果需要总结一句话方向性变化：**修复C01后，暴露侧的临界风速、二次项系数均小幅走高；恢复侧二次项系数也小幅走高，阵风相对customers_v2的解释力权重有所上升（权重比从12.7倍降到7.4倍）；核心的"二次项显著且稳健"这一定性结论在全部检验维度上均未改变，部分稳定性指标（折间CV%）修复后反而改善。** 一个可能相关的现象性观察（不做因果解释）：本次修复涉及的8,199/8,113个受影响事件多为多阶段事件，而多阶段事件通常对应规模更大、持续时间更长的抢修过程，这类事件的"真实最早时刻"阵风读数与"文件行序恰好排在前面的某个后续阶段"读数相比，前者更贴近事件刚发生、天气条件更极端的时刻——这与修复后阵风相关系数普遍略有增大（而非减小）的方向是一致的，但这只是现象层面的观察，本命令未做进一步的因果验证。

## 1. 问题的起点：现有数据是怎么算出customers和duration的

UK Power Networks（UKPN）的原始停电事件数据（`ukpn-iis.csv`）里，一次停电事件（Incident）在恢复过程中可能经历多个"恢复阶段"（Restoration Stage）——比如先恢复一部分客户供电，过一段时间再恢复另一部分，每个阶段都是原始文件里的独立一行记录，共享同一个 Incident Reference。全部237,901行原始记录对应约135,025个唯一事件，平均每个事件约1.76条记录，但分布高度不均：约69.6%的事件只有1条记录，但约30.4%的事件有2条及以上，最多的一个事件有125条记录（详见 `00_原始字段验证.md`）。

用户自建的数据处理脚本 `filter.py`（第9步链路的第1步，详见 `claude_branch/results/pipeline_archaeology/`）在处理这批数据时，用了这样一段逻辑：

```python
df_filtered = df_filtered.sort_values([incident_col, "_sort_time"], kind="stable")
df_unique = df_filtered.drop_duplicates(subset=[incident_col], keep="first").copy()
```

翻译成人话：按事件分组，按开始时间排序后，**每个事件只保留最早的那一条记录，其余全部丢弃**。后续的`data_arrange.py`再用这一条幸存记录自己的起止时间算出`Duration (hours)`。这套逻辑简单、可复现，但有一个根本问题：**它完全没有处理"一个事件有多条记录"这件事本身**——不是"聚合方式不对"，而是压根没有发生任何跨阶段的聚合，其余阶段的数据在第一步就被物理丢弃了。

## 2. 官方要求的是什么（依据，原文引用自工作命令#7正文）

据《RIIO-ED2 Regulatory Instructions and Guidance – Interruptions v1.1》（2024-01-01发布）附录1 §4.2-4.3公式定义，与《RIIO-ED1 Annex F》(2020) 对应条款一致（本命令直接采信网页端在命令正文中给出的转述，未独立重新查证Ofgem原始PDF，这一点在`claude_branch/results/pipeline_archaeology/04_与官方公式差异定位.md`中已有说明，此处沿用同一立场）：

- **CIt**（Customers Interrupted）= `Σᵢ Σᵣ NDrit`，`NDrit`定义为"Number of Customers interrupted in Restoration Stage r of…incident i…**excluding re-interruptions to supply**"——要求跨阶段求和，且要排除标记为"重复中断"的阶段。
- **CMLt**（duration of interruptions to supply）= `Σᵢ Σᵣ NNrit × (TRrit − TIrit)`，`NNrit`定义为"…**including re-interruptions to supply**"——要求跨阶段的、按客户数加权的时长求和，且这次要**包含**重复中断阶段。

两条公式的关键差异（这也是本命令Rule 2设计的直接依据）：**customers要排除重复中断（避免同一批人被反复计数），duration要包含重复中断（这些人确实又断电了一次，这段时长要算进去）**。

## 3. 本命令的重建设计：逐条对应官方公式与代码

### 3.1 取消Cause Code预筛选（规则1）

**原代码位置**：`filter.py`第165-173行：
```python
keep_groups = {"weather_natural", "technical_asset"}
df["keep_for_weather_analysis"] = df["cause_group_official"].isin(keep_groups)
...
df_filtered = df[df["keep_for_weather_analysis"]].copy()
```

**为什么要改**：这一条筛选与customers/duration的计算逻辑本身无关，是一个独立的分析范围选择（只研究天气/技术原因导致的停电）。但它会影响样本量和代表性，构建阶段本身不应该替分析阶段预先做这个选择——保留`cause_group_official`分类标签、不再用它过滤行，让后续任何具体分析可以按需自行筛选。

**新代码位置**：`filter_v2.py`的`generate_event_level_table()`——分类计算逻辑（`normalize_cause_code`/`classify_cause_code`）逐字保留，只是不再有`df_filtered = df[df["keep_for_weather_analysis"]]`这一行过滤。

### 3.2 customers_v2：跨阶段求和、排除重复中断（对应官方CIt）

**官方依据**：CIt = `Σᵣ NDrit`，"excluding re-interruptions to supply"。

**原代码的缺失**：`filter.py`因为在第一步就丢弃了除最早一条外的全部阶段记录，customers的值从始至终是单阶段透传，从未有过求和这个动作。

**新代码实现**：`filter_v2.py`的`_customers_v2()`函数：
```python
def _customers_v2(g):
    eligible = g.loc[~g["_is_excluded_reinterruption"], "_customers_numeric"]
    if len(eligible) == 0:
        return np.nan
    return eligible.sum(skipna=True)
```
按Incident Reference分组，排除`Re-interruption Stage`标记为需要排除的阶段（默认只排除`'Y'`，见3.4节关于'0'/'1'的讨论），对其余阶段的`Number of Customers Restored`求和。

### 3.3 duration_A/duration_B：两种候选的"跨阶段+加权"实现（对应官方CMLt与"Incident completion"概念）

**官方依据**：CMLt = `Σᵣ NNrit × (TRrit−TIrit)`，"including re-interruptions to supply"；另外官方"Incident completion"定义（全部客户持续恢复满3小时/使用临时供电满18小时视为事件完成）是一个独立于CMLt公式的、判定"事件何时算结束"的规则。

**为什么设计两个候选而不是一个**：CMLt公式的"客户数加权时长求和"和"Incident completion"的"全部客户完全恢复的时间点"是两个概念上不同的东西——前者是一个考虑了阶段性、部分恢复的加权指标，后者是一个更贴近直觉的"这次停电到底持续了多久"的总跨度指标。命令原文要求两者并行构建，不预先择一，这也是本命令设计上尊重的一点。

**新代码实现**（`filter_v2.py`）：
```python
def _duration_a(g):
    w = g["_customers_numeric"]; t = g["_stage_duration_hours"]
    valid = w.notna() & t.notna()
    ...
    return (w[valid] * t[valid]).sum() / denom
```
duration_A严格对应CMLt公式的"加权平均"形式（`Σ(NNrit×时长)/Σ(NNrit)`，量纲从"客户·小时"归一化为"小时"，代表该事件的客户数加权平均恢复时长）；`NNrit`按官方要求**包含**重复中断阶段（即不排除`Re-interruption Stage='Y'`的阶段，与customers_v2的排除方向刚好相反,这是有意为之,不是疏漏)。

```python
latest_end = grouped["_end_dt"].max()
earliest_start = grouped["_start_dt"].min()
duration_b = (latest_end - earliest_start).dt.total_seconds() / 3600.0
```
duration_B是"Incident completion"概念的简化实现——**已知局限**：没有实现官方"3小时/18小时完成判定"规则，因为需要一个"是否使用临时供电（Temporary Connection）"的字段才能精确区分，而Step 1未能确认原始数据中存在这样一个可直接使用的字段（codex的`audit_step0d/00d_three_minute_rule_audit.csv`审计的是阶段级最短记录时长的技术判定，不是"是否使用临时供电"这个业务字段本身）。命令原文明确授权在找不到该字段或实现复杂度过高时先用最简单的"最晚End−最早Start"，本命令按此执行，此处如实注明这一简化。

### 3.4 边界情况：全部阶段都是重复中断

**官方依据**：无（这是本命令为了代码健壮性主动设计的防御性检查，不对应具体官方条款）。

**原因**：如果一个事件的全部阶段记录都被判定为"应排除的重复中断"，`customers_v2`的求和范围就是空集，直接`sum()`会返回0，这会把"没有数据"错误地混同于"客户数确实是0"两种完全不同的情况。`filter_v2.py`通过`all_stages_are_reinterruption`标记列显式区分这种情况，并将`customers_v2`设为`NaN`而非静默输出0。

### 3.5 未解决的歧义：`Re-interruption Stage`的'0'/'1' legacy编码

**证据**：`Re-interruption Stage`字段实测有四种取值：N（91.33%）、Y（8.63%）、0（0.041%，仅RIIO-ED1时期）、1（0.0008%，同上）。官方公式转述里只提到"re-interruptions"这一个二元概念，没有说明'0'/'1'这两个legacy取值该如何归类。

**本命令的处理方式**：`filter_v2.py`把这个判断封装成一个独立常量`REINTERRUPTION_EXCLUDE_VALUES = {"Y"}`，默认只把明确标记为`'Y'`的阶段视为"应排除的重复中断"，'0'/'1'（连同缺失情形，虽然实测缺失率为0）默认视为"非重复中断"（计入customers_v2求和）。这是一个**待确认的默认假设**，不是确凿依据——codex自己独立审计的`00b_raw_stage_audit_report.md`同样把这个问题标记为"尚需人工确认"（D3/D9决策门）。选择把它做成一个显式常量而不是散落在函数逻辑里的魔法值，是为了让未来任何人只需要改一行常量定义，不需要改动聚合函数本身的逻辑结构。

### 3.6 LAD合并逻辑：零改动，原样复用

**依据**：用户明确说明这部分逻辑"已经解决过真实困难问题"（2020年白金汉郡单一管理区改革的人口加权crosswalk），命令原文硬性约束3明确要求"原样复制、不做任何逻辑改动"。

**核实方式**：`match_lad.py`、`Buckinghamshire_combination.py`、`LAD_GeoMerge.py`及LAD地理子链三脚本（`LAD_AreaSummary.py`/`LAD_urban_Summary.py`/`LAD_DNO.py`），复制到`claude_branch/scripts/pipeline_v2/`前后分别计算了SHA256哈希，逐一确认复制前后哈希完全一致（详见`claude_branch/scripts/pipeline_v2/00_LAD脚本零改动哈希校验.txt`），证明这是逐字节相同的复制，不存在任何改动。

## 4. 与命令#6结论的衔接

本命令的重建设计直接建立在命令#6（修正版）的考古结论之上：命令#6精确定位了customers/duration偏离官方口径的唯一根源是`filter.py`的`drop_duplicates(keep="first")`，并明确指出"LAD合并逻辑应原样复用、customers/duration计算逻辑需要修改"——本命令正是沿着这个结论，把"需要怎么改"从命令#6的概念性描述，落实成了具体可执行的代码（`filter_v2.py`）。命令#6同时指出的"改动规模判定为中等偏大"这一预判，在本命令的实际实现中得到印证：确实只需要在`filter.py`的dedup步骤之前插入聚合逻辑（本命令新增约150行代码），并简化`data_arrange.py`的duration计算，其余LAD/人口/GVA下游步骤完全不受影响，不需要"整个数据读取结构重写"。

# Step 6：下游重跑规模评估

本命令不要求跑完整个九步链路（天气匹配、LAD合并等），只评估规模，为网页端/用户决定"是否值得、什么时候执行完整重跑"提供依据。以下数字全部来自codex已经独立计算并留存在项目目录里的聚合统计（非本命令自己对原始数据的新计算——Step 0的阻塞点同样适用于这里，本命令没有能力独立验证这些数字，只是转引并做推算）。

## 1. 新增事件数量估算

### 已知数字（均直接来自codex审计脚本对全部237,901行原始数据的实际计算）

| 数字 | 来源 |
|---|---|
| 原始文件总行数：237,901 | `audit_reinterruption_stage.py`实际统计 |
| 原始文件唯一Incident Reference数（不限Cause Code）：135,025 | 同上 |
| `filter.py`按weather_natural+technical_asset筛选+去重后的行数：66,080 | 命令#6已核实（`filter.py`实际输出文件行数） |
| `main1.py`处理后（dropna坐标/时间解析失败）的最终行数：62,928 | 命令#6已核实 |

### 推算逻辑

`main1.py`对已经过Cause Code筛选的66,080行做坐标/时间解析清洗后，保留62,928行，**保留率为 62,928/66,080 = 95.23%**。

若取消Cause Code预筛选（规则1），候选事件总数从66,080（经Cause Code筛选+去重后）变为135,025（全部原始数据的唯一事件数，未经任何Cause Code筛选，且这是`filter_v2.py`聚合后的事件级行数上限，因为聚合是"每个incident一行"而不再是按阶段展开）。

**假设`main1.py`的坐标/时间解析失败率在不同Cause Code分组之间大致均匀**（这是一个未经验证的假设，如实标注），按同样95.23%的保留率推算：

```
135,025 × 0.9523 ≈ 128,589 行（估算的新版最终事件数上限）
```

**新增事件数估算：128,589 − 62,928 ≈ 65,661 个（相对当前62,928行增加约104%，接近翻倍）**

### 估算的不确定性（如实标注）

1. "保留率均匀"这一假设未经验证——被Cause Code筛选掉的third_party/human_error/external_or_customer/non_fault_or_unknown四类事件，其坐标/时间字段的完整性未必与weather_natural/technical_asset两类一致（例如第三方施工导致的停电，记录规范性可能不同），实际保留率可能高于或低于95.23%。
2. `filter_v2.py`的技术性清洗步骤（剔除Start/End无法解析的行）本身也会在聚合阶段之前先丢弃一部分阶段记录，这与`main1.py`的dropna有一定重叠但不完全相同（`filter_v2.py`只清洗时间字段，`main1.py`还包含坐标字段），因此上述95.23%这个比率不是精确适用的转换系数,只能作为数量级参考。
3. 因此，65,661这个数字应理解为**约6万至7万量级的新增事件**，不是精确预测,建议实际执行`filter_v2.py`（在Step 0阻塞解除后）得到确切数字。

## 2. 新增事件在现有天气缓存中的命中率

**无法直接查询验证**：本次会话没有`device_bash`权限，无法对`.weather_cache_master.sqlite`（514MB）执行SQL查询来精确统计缓存命中率。

**定性推理（非精确数字）**：现有62,928行事件全部属于weather_natural/technical_asset两类Cause Code，其天气缓存是围绕这些事件的具体时间+坐标窗口建立的。新增的约6-7万个事件，其Cause Code属于third_party/human_error/external_or_customer/non_fault_or_unknown四类，是**此前从未被`main1.py`处理过的全新事件记录**——除非某个新增事件恰好与某个现有事件共享完全相同的取整小时+坐标窗口（这在同一变电站短时间内发生多次不同原因停电时有可能，但预期是少数情况），否则绝大多数新增事件都需要重新调用Open-Meteo历史天气API,缓存命中率预期接近0%，而不是较高比例。

**建议**：如果需要精确数字，应在`device_bash`可用（或用户本机可执行）的环境下，对`.weather_cache_master.sqlite`按新增事件的时间+坐标做一次实际查询统计，而不是依赖本命令的定性推测。

## 3. 完整重跑九步链路到374列版本的工作量判断

### 已知的间接线索

- `.weather_cache_master.sqlite`当前大小514MB，覆盖当前62,928行事件的天气窗口数据。
- `main1.py`脚本本身28,401字节，内部逻辑包含"调用并缓存Open-Meteo历史天气API"的流程,并有检查点文件`weather_checkpoint.json`用于支持中断后恢复,说明这是一个已知会运行较长时间、需要断点续跑机制的脚本。

### 无法量化的部分（如实标注,不猜测具体小时数）

本命令没有获得`main1.py`实际运行62,928行数据所花费的具体时间数据（比如"上次全量运行耗时X小时"这样的记录未在可读取的项目文档中找到），也没有Open-Meteo API的速率限制/并发数等参数信息。因此**无法给出一个具体的"完整重跑需要几小时/几天"的数字**——给出这样一个数字而没有实际依据,是编造,不是评估。

### 可执行的下一步判断依据（具体、可操作，而非"需要评估"这种空话）

建议按以下方式获得真实依据，而不是本命令凭空估计：
1. **小规模计时测试**：从新增的约6-7万个候选事件中随机抽取100个（或某个小批量），实际运行一次`main1.py`的天气匹配逻辑（在有权限执行的环境下），记录实际耗时，然后按比例线性外推到全部6-7万个新增事件——这是一个可以在几分钟到几十分钟内做完的小实验，能给出比任何理论推算都更可靠的数字。
2. **缓存命中率实测**：同一批100个测试事件，统计其在`.weather_cache_master.sqlite`中的实际命中情况，验证第2节"预期接近0%"这一定性推断是否成立。
3. 在获得第1/2点的实测数据之前，**建议网页端/用户不要贸然启动全量九步链路重跑**，因为：(a) Step 0的原始数据阻塞尚未解除，`filter_v2.py`本身还没有真实数据可用；(b) 即使阻塞解除，一次约6-7万新增事件的天气API重新匹配，在没有实测耗时数据的情况下贸然启动，存在长时间运行后才发现速率限制/网络问题导致中途失败的风险，应先做小规模验证。

## 4. 小结：给网页端/用户的建议

- 新增事件数量级：约6-7万个（现有62,928的约104%），量级明确但精确数字待`filter_v2.py`在真实数据上跑通后确认。
- 天气缓存命中率：预期接近0%（定性推理,非实测），建议实测验证。
- 完整重跑耗时：无可靠依据给出具体数字，建议先做100个事件规模的计时测试再决定是否启动全量重跑。
- **最优先级仍然是解除Step 0的原始数据访问阻塞**——没有真实数据，`filter_v2.py`本身都无法验证，遑论下游九步链路的完整重跑。

### 已尝试的替代方案（按命令要求，不是第一次失败就放弃）

1. **检查是否有 `device_bash`（可在用户设备上执行分块读取）工具**：`ToolSearch` 查询确认本次会话没有连接任何 `device_bash` 类工具，无法在设备本机对文件做分块/流式读取。
2. **检查是否存在已有的原始数据子集/样本文件**：浏览了 `data/1/`、`data/first_step_weather_tests/` 等目录，均为无关内容（Excel比对文件、天气回归中间产物），未发现任何现成的原始阶段级数据子集或样本。
3. **检索项目内是否有其他脚本已经独立读取过原始文件、并留下可复用的产出**：这是本次真正找到实质性替代信息的方向，详见下方"通过 codex 独立脚本获得的信息"。

### 通过 codex 独立脚本获得的信息（重要说明：这是本命令唯一能够获得的关于原始文件内容的信息来源）

在 `audit_reinterruption_stage/`、`audit_step0/`、`audit_step0b/`、`audit_step0e/` 等目录下，发现 codex 此前已经写过多个**直接读取 `data/ukpn-iis.csv` 原始文件**的独立只读审计脚本（`audit_reinterruption_stage.py`、`audit_step0e/canonicalise_stage_data.py` 等），并且已经运行过，留下了实际计算结果（CSV/parquet）。这些脚本的源代码本身，以及它们的实际输出数值，构成了本命令目前能够获得的、关于原始文件字段名和取值分布的**唯一直接证据**。

**必须明确说明这不等同于本命令自己验证了原始文件**：以下 Step 1 的全部结论，都是"读取 codex 脚本的源代码 + 读取该脚本已经算出来的实际输出数值"得到的，不是本命令自己在沙箱里对 `ukpn-iis.csv` 跑了一次 `pd.read_csv()` 得到的。这个区别很重要——源代码本身能确凿证明"某个字段名的确切拼写"，但本命令没有独立复现过这些计算。

**尤为重要的是，本命令在核查过程中发现了 `audit_step0e/outcome_builder.py`——codex 自己也曾试图构建与本命令Rule 2完全同类的"事件级客户数/时长聚合"逻辑，但把它自己明确禁用了**：

### ⚠️ 本命令的决策边界（严格遵照命令原文要求，未越界）

命令原文明确写道："间接来源（codex审计报告）不足以支撑重新计算customers/duration这么核心的工作"，"如果第三次仍然失败，这是一个需要网页端和用户共同决定下一步怎么办的重要阻塞点，不要自行决定放弃或用间接数据源顶替"。

`audit_step0e/00e_canonical_stage_rows.parquet` 事实上是一份**逐行保留的、经哈希校验、已与当前最终主数据文件做过100%交叉匹配验证**（62,928/62,928 全部匹配，见 `00e_data_quality_summary.csv`：`legacy_crosswalk_rows=62928, legacy_crosswalk_full_matches=62928`）的原始文件"规范化副本"——理论上完全可以拿来当作本命令 Step 3/4 的计算底稿。**但本命令没有这样做**，因为：
1. 这仍然是 codex 独立产出的文件，不是本命令自己对原始文件的直接读取；
2. 是否接受"用 codex 已建好的规范化副本代替我自己读取原始文件"这个替代方案，其性质已经超出本命令"如实报告阻塞点"的授权范围，属于命令原文明确指出的"需要网页端和用户共同决定"的问题，不应由执行者单方面决定。

**因此，本命令在 Step 0 层面的结论是：原始文件三次传输均失败，具体错误信息如上；已找到的、可能的技术性解决路径（授权使用 codex 的 `audit_step0e/00e_canonical_stage_rows.parquet` 规范化副本作为计算底稿）已经列出，但采用与否需要网页端/用户明确拍板，本命令不做代为决定。** 详见本文档末尾"给网页端/用户的决策请求"一节。

在此阻塞点之下，本命令按以下方式安排后续工作：Step 1（字段验证）依然可以基于 codex 脚本的**源代码**给出确凿证据（不需要执行原始数据，只需要读代码字符串本身），因此照常完成；Step 2（复制脚本）、Step 5（方法论文档）不依赖原始数据，照常完成；Step 3（编写聚合代码）可以完成代码本身并用合成数据自测，但明确标注"未在真实数据上执行过"；Step 4（产出新版基础表+差异对比）**无法用真实数据完成**，本命令没有伪造或用间接数据顶替，而是详细说明了"一旦解除阻塞后应该怎么算"；Step 6（下游重跑规模评估）使用 codex 已经独立算出的、公开的聚合计数（如"原始文件共237,901行、135,025个唯一事故"）做规模估算——这类"引用已有的、非本命令核心计算目标的规模性事实"，与命令原文特别指出的"customers/duration核心重算不能用间接来源顶替"是两回事，故未越界。

## Step 1：关键字段验证

以下全部字段名和取值分布，均来自对 codex 两个独立脚本源代码的直接阅读（`audit_reinterruption_stage/audit_reinterruption_stage.py` 与 `audit_step0e/canonicalise_stage_data.py`，两者互相独立编写，但读取同一 `data/ukpn-iis.csv` 时使用的字段名完全一致，形成交叉验证），以及这两个脚本已经算出的实际输出数值。

### 确认的原始字段清单（非猜测，逐字取自脚本代码里的 `pd.read_csv(..., dtype={...})` 字段名字符串）

| 字段名（原始，确切拼写） | 用途 | 备注 |
|---|---|---|
| `Incident Reference` | 事故唯一标识 | 需 `.str.strip()` 清理空格后才能用作分组键（两个脚本均如此处理） |
| `Restoration Stage` | 恢复阶段序号 | 数值型（含字符串形式的数字），已见取值 1 至 140+ |
| `Re-interruption Stage` | 重复中断标记 | **不是命令原文假设的"Re-interruption"，确切字段名是"Re-interruption Stage"** |
| `Start Date and Time` | 阶段开始时间 | |
| `End Date and Time` | 阶段结束时间 | |
| `Number of Customers Restored` | 该阶段客户数 | 原始为字符串类型，需数值化 |
| `Cause Code` | 停电原因代码 | 与 `filter.py` 的 `normalize_cause_code()`/`classify_cause_code()` 完全对应 |
| `MEI code` | （新发现，此前命令#6未记录）| 出现在 `canonicalise_stage_data.py` 的 `KEY` 字段列表里，具体业务含义本命令未展开核实（不在customers/duration/LAD三条核心线内），如实记录其存在 |
| `Spatial Coordinates` | （新发现，此前命令#6未记录）| 同上，出现在 `KEY` 字段列表里，`main1.py` 的坐标解析大概率是从这个字段或类似字段派生 lat/lon，本命令未逐行重新核实 `main1.py` 对此字段的具体解析方式（不在本命令改动范围内） |

### `Re-interruption Stage` 字段的确切取值分布（直接来自 `audit_reinterruption_stage.py` 对全部237,901行的实际计算，非估计）

| `Y` | 20,525 | 8.63% | 是重复中断 |

`missing_reinterruption` 实测为 **0**——即该字段在全部237,901行中没有缺失值，每一行都有取值（N/Y/0/1 四选一）。

### 交叉表证据：`Re-interruption Stage='Y'` 主要出现在 Restoration Stage≥2 的阶段

`reinterruption_x_restoration_stage.csv` 的交叉表证实：Restoration Stage=1 的记录几乎全部标记为 `N`（RIIO-ED1: 78,718个N对32个Y；RIIO-ED2: 41,959个N对7个Y），`Y` 主要集中出现在 Restoration Stage=2及以上的记录——这与"Re-interruption 是指同一批客户在后续阶段被再次中断"的业务解释一致（该解释来自命令原文0.2节的官方定义转述，本命令未独立查证Ofgem原文，只是确认原始数据的实际分布与该解释在方向上不矛盾）。

### `Number of Customers Restored` 与 Cause Code 的取值范围

- `Number of Customers Restored`：原始为字符串类型，需数值化（`pd.to_numeric`）后使用；在当前62,928行最终数据集里（单阶段透传值）范围为0至11,423，中位数1，均值31.3（`00_outcome_quality.csv`，command#6已引用）。
- `Cause Code`：字符串类型，存在补零（如'06'）与不补零（如'71'）两种表示方式并存的情况，`filter.py`的`normalize_cause_code()`已处理这一归一化问题（command#6已详细记录）。

### 未能验证的事项（如实记录）

1. **`MEI code`、`Spatial Coordinates` 两个字段的具体业务含义和取值范围**——本命令仅确认其字段名存在于原始文件中（来自`canonicalise_stage_data.py`的KEY列表），未展开核实其具体内容，因为这两个字段不在本命令customers/duration/LAD三条核心线内。
2. **`Re-interruption Stage`取值为'0'/'1'的业务语义**——如Step 0所述，这是本命令Rule 2实现中`REINTERRUPTION_EXCLUDE_VALUES`常量选择的核心不确定性来源，codex自己的独立审计（`00b_raw_stage_audit_report.md` D3/D9）也将其列为"尚需人工确认"，本命令未能解决这一根本性歧义，只能在代码里做出一个可复核、可调整的默认假设（详见`01_新版基础表校验.md`与`filter_v2.py`源码注释）。
3. **原始文件本身未能在本次会话中被直接读取**——如Step 0所述，这是本命令最主要的未决事项。

# Step 3：逐脚本详细文档

以下按 Step 2 链路顺序逐一说明。**customers/duration 计算逻辑**（`filter.py`、`data_arrange.py`）与 **LAD 合并逻辑**（`match_lad.py`、`Buckinghamshire_combination.py`、`LAD_GeoMerge.py`）按命令要求精确到代码片段，其余脚本给出摘要说明。

## 1. `filter.py`（★ customers 计算逻辑的关键一步）

**目的**：从原始 IIS 记录中筛选出天气/自然与设备/资产两类原因的事件，并按 Incident Reference 去重。

**核心代码（第 160-189 行，原样引用）**：

```python
# 标准化 Cause Code
df["cause_code_norm"] = df[cause_col].apply(normalize_cause_code)
df["cause_group_official"] = df["cause_code_norm"].apply(classify_cause_code)

# 严格筛选：仅保留天气/自然 + 技术/资产故障
keep_groups = {"weather_natural", "technical_asset"}
df["keep_for_weather_analysis"] = df["cause_group_official"].isin(keep_groups)
...
excluded_df = df[~df["keep_for_weather_analysis"]].copy()
df_filtered = df[df["keep_for_weather_analysis"]].copy()

# 若有时间列，先排序，确保去重时保留最早事故记录
if time_col is not None:
    df_filtered["_sort_time"] = pd.to_datetime(
        df_filtered[time_col], errors="coerce", utc=True
    )
    df_filtered = df_filtered.sort_values([incident_col, "_sort_time"], kind="stable")
else:
    df_filtered = df_filtered.sort_values([incident_col], kind="stable")
...
df_unique = df_filtered.drop_duplicates(subset=[incident_col], keep="first").copy()
```

**★ 这是 customers/duration 口径与 Ofgem 官方公式产生分歧的第一个、也是最根本的一步**：`time_col` 是 `Start Date and Time`（"start"+"time" 关键词匹配到的列），`drop_duplicates(subset=[incident_col], keep="first")` 意味着**对每个 `Incident Reference`，只保留时间最早的那一条 Restoration Stage 记录，其余所有 Restoration Stage 记录（包括各自的 `Number of Customers Restored` 和起止时间）全部被丢弃**。这个去重发生在整条链路的第一步，**在此之后的所有脚本都只处理这一条幸存记录，不会再接触到被丢弃的其他 stage**。

**未涉及 customers=0 的任何特殊处理**：代码里没有任何一行单独判断或过滤 `Number of Customers Restored == 0` 的情况——0 值（如果原始最早那条 stage 记录本身就是 0）会原样保留到输出中（详见 `05_customers为0情况说明.md`）。

## 2. `main1.py`（天气特征构建，不涉及 customers/duration）

**目的**：解析事故发生时间和坐标，调用 Open-Meteo 历史天气 API，构造事发时刻（`_0h`）及 6/12/24/48/72 小时窗口的天气特征。

**摘要**：`prepare_incident_time()` 把 `Start Date and Time` 解析为 UTC 时间 `clean_start`；`parse_spatial_coordinates()` 从 `Spatial Coordinates` 提取 `lat`/`lon`；`round_coordinates()` 四舍五入到 1 位小数以合并重复的天气请求（`lat_r`/`lon_r`）；随后逐行调用 `fetch_weather_for_request()`，用磁盘缓存（`.weather_cache_master.sqlite` + `data/weather_request_cache`）避免重复请求。第 545 行 `df = df.dropna(subset=["clean_start", "lat", "lon"]).copy()` 是本步骤唯一的行筛选点——这正是链路里"66,080 行 → 62,928 行"这一下降发生的位置（时间或坐标解析失败的记录被丢弃）。**不涉及 customers/duration 的任何读取或计算**。

## 3. `match_lad.py`（★ LAD 合并逻辑之一：空间连接）

**目的**：把每条停电记录按经纬度落点匹配到其所在的 LAD（Local Authority District）。

**核心代码（第 39-65 行，原样引用）**：

```python
gdf_points = gpd.GeoDataFrame(
    df,
    geometry=gpd.points_from_xy(df["lon"], df["lat"]),
    crs="EPSG:4326"
)
lad = gpd.read_file(lad_shp)
lad = lad.to_crs("EPSG:4326")

gdf_matched = gpd.sjoin(
    gdf_points,
    lad,
    how="left",
    predicate="within"
)
```

**方法**：纯粹的**点落区空间连接（point-in-polygon spatial join）**，用 `geopandas.sjoin(..., predicate="within")`，把每个停电事件的经纬度坐标点与 ONS 提供的 LAD（2021年12月版）边界多边形做空间包含关系匹配，得到 `LAD21CD`/`LAD21NM`。这是一种"坐标空间匹配"，不是行政区代码直接匹配（因为原始 IIS 数据本身没有 LAD 代码字段，只有经纬度）。匹配失败率通过 `missing_rate = gdf_matched[lad_code_col].isna().mean()` 打印，但代码里**没有对匹配失败记录做任何后续修复或剔除**，缺失的 LAD 字段会以 NaN 形式带入下一步。

## 4. `poppulation_merge.py`（人口合并，不涉及 customers/duration/LAD 匹配方法本身）

**目的**：把 ONS 人口宽表（`*_YYYY` 格式列）转换为 LAD-年份长表，再按 `LAD21CD` × `year` 合并进事件表。`year` 由事件的 `clean_start` 年份提取（第 144-149 行）。合并方式是标准 `pd.merge(..., on=["LAD21CD","year"], how="left")`（第 161-166 行），直接假设人口表的 `LAD23CD` 与事件表的 `LAD21CD` 编码兼容（脚本注释中承认"不保证100%一致，后面若缺失率高再做crosswalk"）。

## 5. `Buckinghamshire_combination.py`（★ LAD 合并逻辑之二：Buckinghamshire 新旧区划人口加权 crosswalk——用户明确要求原样保留的部分）

**目的**：合并英国 2019 年剥夺指数（IMD）与城乡分类数据，并处理 2020 年英国地方政府重组中 Buckinghamshire 四个旧区（Aylesbury Vale / Chiltern / South Bucks / Wycombe）合并为单一新统一制机构（Buckinghamshire, `E06000060`）这一行政区划变更。

**核心代码（第 25-32 行，手动 crosswalk 映射表，原样引用）**：

```python
MANUAL_CROSSWALKS = [
    {
        "new_code": "E06000060",
        "new_name": "Buckinghamshire",
        "old_codes": ["E07000004", "E07000005", "E07000006", "E07000007"],
        "old_names": ["Aylesbury Vale", "Chiltern", "South Bucks", "Wycombe"]
    }
]
```

**核心代码（第 168-184 行，数值列人口加权平均逻辑，原样引用）**：

```python
for col in numeric_cols:
    x = pd.to_numeric(old_subset[col], errors="coerce")
    if x.notna().sum() == 0:
        new_row[col] = np.nan
        continue
    if use_weight:
        w = old_subset["population"]
        valid = x.notna() & w.notna()
        if valid.sum() == 0:
            new_row[col] = x.mean()
        else:
            new_row[col] = np.average(x[valid], weights=w[valid])
    else:
        new_row[col] = x.mean()
```

**方法**：这不是空间匹配，而是**行政区代码的人工映射表（crosswalk）+ 数值型指标按 2021 年人口加权平均、类别型指标取众数**的合并方式。具体做法：先从 IMD 表里取出四个旧 LAD 代码对应的行，关联 2021 年人口（`pop_2021`，来自 `population_lad_long.csv`），如果四个旧区的人口数据都齐全就用人口加权平均（`np.average(x, weights=w)`）合成新 Buckinghamshire 的剥夺指数，否则退化为简单平均；类别变量（如 `rural_urban_classification`）取众数（第 160-166 行）。构造完新行后追加进 IMD 表（`pd.concat` + `drop_duplicates(keep="last")`），再按 `LADCD` 做标准 left merge 合并进主表（第 213-218 行）。**这套 crosswalk 逻辑在下一步 `GVA_merge_with_crosswalk.py` 里被完全重复使用**（同样的四个旧代码、同样的新代码、同样的人口加权求和/重算逻辑，只是数值列换成了 GVA 总量类指标且改用"求和"而非"加权平均"，因为 GVA 总量是可加的）。

## 6. `GVA_new.py` / `GVA_merge_with_crosswalk.py`（GVA/行业结构合并）

**目的**：提取 2016 年 LAD 级 GVA（Gross Value Added）及行业构成数据并合并进主表；同样处理 Buckinghamshire crosswalk，但因为 GVA 是总量指标，用的是**人口加权求和**（`new_row[col] = pd.to_numeric(gva_old[col]).sum()`，第 63-64 行）而不是加权平均，`gva_pc`（人均GVA）用"总GVA/总人口"重新计算（第 66-69 行），行业占比 `_share` 系列在合并总量后重新计算比例（第 91-97 行）。**这部分变量（GVA/行业结构）目前不在 `0519_4.*` 核心模型公式里使用**（`database_lineage.md` 第 210 行已指出这一点），但保留在最终数据库中。

## 7. `LAD_AreaSummary.py` → `LAD_urban_Summary.py` → `LAD_DNO.py`（LAD 地理/DNO 特征三步子链路）

摘要：`LAD_AreaSummary.py` 用 LAD shapefile 直接算面积（`geometry.area / 1e6`）；`LAD_urban_Summary.py` 把 LAD 边界与 2022 年 BUA（建成区）边界求几何交集（`gpd.overlay(..., how="intersection")`），按 LAD 汇总交集面积得到 `bua_area_km2`，除以 LAD 总面积得到 `urban_ratio`（英格兰/威尔士/苏格兰适用，北爱尔兰因 BUA 数据不覆盖而保持缺失）；`LAD_DNO.py` 把 LAD 边界与 DNO（配电网运营商）牌照区边界求交集，每个 LAD 选**重叠面积最大**的 DNO（`groupby("LAD21CD").first()`，按重叠面积降序排序后取第一行），北爱尔兰单独手动指定为 `NIE Networks`（无 GB DNO 数据覆盖）。三步都是几何运算，不涉及事件级 customers/duration。

## 9. `data_arrange.py`（★★ duration 计算逻辑——本命令最核心的发现）

**目的**：从起止时间戳计算 `Duration (hours)` 及其他时间派生字段，是产出最终 `ukpn_master_with_lad_features_updated.csv` 的最后一步。

**完整核心代码（第 17-52 行，原样引用，未删减）**：

```python
start_col = "Start Date and Time"
end_col = "End Date and Time"

df[start_col] = pd.to_datetime(df[start_col], errors="coerce", utc=True).dt.tz_convert(None)
df[end_col] = pd.to_datetime(df[end_col], errors="coerce", utc=True).dt.tz_convert(None)

# Duration (hours)
duration = (df[end_col] - df[start_col]).dt.total_seconds() / 3600
duration[duration < 0] = pd.NA

# Daytime Indicator
start_hour = df[start_col].dt.hour
daytime = ((start_hour >= 6) & (start_hour < 18)).astype("Int64")

# 时间结构变量
hour = start_hour
month = df[start_col].dt.month
weekday = df[start_col].dt.weekday  # 0=Monday, 6=Sunday
```

**★★ 这是 duration 计算逻辑的唯一位置，逻辑极其简单**：`Duration (hours) = (End Date and Time − Start Date and Time) 的总秒数 / 3600`，**对 `filter.py` 去重后幸存的那唯一一条（最早的）Restoration Stage 记录**计算首尾时间差。**没有任何跨 Stage 求和、没有按客户数加权、没有处理 Re-interruption（重复中断）标记**。唯一的清洗是把负值（时间顺序颠倒，可能是数据录入错误）设为缺失（`duration[duration < 0] = pd.NA`）。

## Customers 计算逻辑：跨脚本追溯结论

对全部已核实脚本（`filter.py`、`main1.py`、`match_lad.py`、`poppulation_merge.py`、`Buckinghamshire_combination.py`、`GVA_new.py`、`GVA_merge_with_crosswalk.py`、`LAD_AreaSummary.py`、`LAD_urban_Summary.py`、`LAD_DNO.py`、`LAD_GeoMerge.py`、`data_arrange.py`）做了关键词搜索（`grep -r "Customer"`），**在整条九步主链的任何一个脚本里，都没有找到任何一行代码读取、计算、聚合或修改 `Number of Customers Restored` 这一列**。唯一提到这个列名的两处代码是：

1. `deeprig.py`（不在主链上，是一个独立的建模脚本）第 101 行：`df["customers_restored"] = safe_num(df["Number of Customers Restored"])`——只是把已经在最终主表里的原始值做数值类型强制转换，不是计算。
2. `analysis_step3/run_baseline_models.py`（codex 的独立重构脚本，非用户自建代码）里的注释文字。

**结论：`Number of Customers Restored` 在最终 master CSV 里的值，等于 `filter.py` 去重步骤幸存下来的那唯一一条（每个 Incident Reference 最早的）Restoration Stage 记录里，原始 IIS 数据该列的原始值，从未被任何脚本重新计算、聚合或跨阶段求和过。** 这与 duration 的情况完全对称——两者都是"对被去重丢弃到只剩一条记录的单一 Stage 做直接读取"，而不是 Ofgem 官方 CI/CML 公式要求的"跨 Restoration Stage 聚合"。

## (a) 应原样复用的逻辑（"已解决,不要重新实现"）

以下逻辑经 Step 3 代码级精确核实,判定为已经妥善解决了真实存在的技术难题,后续任何修改 customers/duration 计算逻辑的工作都**不应触碰**这些部分,应直接复用现有脚本或其核心函数:

1. **LAD 空间连接（`match_lad.py`）**——基于 `geopandas.sjoin(gdf_points, lad, how="left", predicate="within")` 的点落区匹配逻辑,使用 `LAD_DEC_2021_UK_BGC.shp`（EPSG:4326）,是标准且正确的空间连接实现,无需改动。

2. **Buckinghamshire 2020 单一管理区改革人口加权 crosswalk（`Buckinghamshire_combination.py` + `GVA_merge_with_crosswalk.py`）**——这是用户明确点名"已经解决的真实困难问题"。核心逻辑:
   - 手工 crosswalk 映射表 `MANUAL_CROSSWALKS`,将旧的四个 LAD 代码（E07000004/E07000005/E07000006/E07000007）映射到新代码 E06000060；
   - 连续型/比率型变量（剥夺指数等）用人口加权平均 `np.average(x[valid], weights=w[valid])`；
   - 可加总型变量（GVA 总量）用直接求和；
   - 分类变量用众数填补。
   
   这套逻辑被**两个独立脚本一致复用**（`Buckinghamshire_combination.py` 处理剥夺/城乡数据,`GVA_merge_with_crosswalk.py` 处理 GVA 数据）,说明这是经过深思熟虑、跨数据源验证过的标准处理方式,**必须原样保留,任何未来的 customers/duration 重算工作都不应影响这部分逻辑,也不需要因为 customers/duration 逻辑变化而调整这里的任何代码**。

3. **LAD 地理特征子链（`LAD_AreaSummary.py` → `LAD_urban_Summary.py` → `LAD_DNO.py`）**——三步分别计算 LAD 面积、建成区比例（与 BUA 2022 边界求交集）、DNO 牌照区覆盖（与 DNO 边界求交集,取最大重叠区,并对北爱尔兰做了 "NIE Networks" 的手工特殊赋值）。这是独立于事件级主链的 LAD 级参考表构建,逻辑自洽,与 customers/duration 无关,原样复用。

4. **`LAD_GeoMerge.py` 最终 LAD 特征合并**——标准的按 `LADCD` 字符串标准化后左连接,逻辑简单可靠,原样复用。

5. **人口/GVA 合并（`poppulation_merge.py`、`GVA_new.py`）**——宽表转长表、按 LAD21CD × year 合并,逻辑标准,原样复用。

6. **`filter.py` 中的 Cause Code 分类逻辑本身（`normalize_cause_code()`/`classify_cause_code()`,不含 dedup 部分）**——Ofgem Annex F Appendix 3 的六组分类（weather_natural/technical_asset/third_party/human_error/external_or_customer/non_fault_or_unknown）及具体代码归组,经核实与 Ofgem 官方文件的分组结构一致,**这部分分类逻辑应保留**,需要修改的只是紧随其后的 dedup 步骤（见下方 (b)）。

**复用建议的具体做法**：未来若要重新实现 customers/duration 计算,建议的最小改动路径是"新增一个聚合步骤,插入在 `filter.py` 的 Cause Code 分类之后、dedup 之前",其余全部脚本（`main1.py` 及之后的 8 个脚本）保持逻辑不变,只需要确认它们读取到的是"聚合后的 customers/duration 字段",不需要重写。

## (b) 唯一需要修改的逻辑：customers 与 duration 计算

**根本原因定位（单一代码位置）**：`filter.py` 中的

```python
df_filtered = df_filtered.sort_values([incident_col, "_sort_time"], kind="stable")
df_unique = df_filtered.drop_duplicates(subset=[incident_col], keep="first").copy()
```

这一行 dedup 逻辑是整条链路中，**唯一**导致 customers 和 duration 两个核心变量偏离官方 Ofgem CIt/CMLt 定义的技术根源。原始数据每个 incident 平均约 3.6 条 Restoration Stage 记录（237,901 行原始数据 / 约62,928-66,080 个唯一 incident，来自 codex 独立审计的 `audit_reinterruption_stage` 报告，本命令因原始文件无法传输沙箱而未能直接复核这一比例，属于交叉引用），dedup 后只保留时间最早的一条，其余全部丢弃。

**customers（`Number of Customers Restored`）**：全程原样透传,从未被任何脚本重新计算、聚合或加总过（`03_脚本详细文档.md` 末尾的全库 grep 结论：仅 `deeprig.py` 出现过一次类型转换,非聚合）。当前值 = 该 incident 最早一条 Restoration Stage 记录的原始客户数,不是官方要求的"跨阶段求和、排除重复中断"的去重计数。

**duration（`Duration (hours)`)**：`data_arrange.py` 用单一幸存记录的 `(End Date and Time - Start Date and Time) / 3600` 计算,不涉及任何客户数加权,也不涉及跨阶段时长累计。当前值 = 该 incident 最早一条记录自身的起止时间差,不是官方要求的"按客户数加权、含重复中断"的 CMLt 口径。

**修改方向（概念性,非完整新代码）**：
1. 在 `filter.py` 的 Cause Code 分类之后、`drop_duplicates` 之前,新增一个"按 incident 分组聚合"步骤,需要引入目前完全未被读取的 `Re-interruption Stage` 字段,依据官方规则（Ofgem ED1 Annex F 2020 para 2.59）实现:
   - 计算聚合后的 customers 值（跨阶段、排除重复中断的去重计数）；
   - 计算聚合后的 duration 值（按客户数加权、含重复中断的时长）。
2. 现有的 `drop_duplicates(keep="first")` 之后的"保留一条代表行"这个动作本身可以保留（下游脚本仍然假设一个 incident 一行）,只是这条代表行上的 customers/duration 两个字段需要替换为新聚合出的值,而不是简单沿用最早一条记录的原始值。
3. `data_arrange.py` 的改动相应简化为：不再自己计算 Duration,而是直接读取 `filter.py` 新聚合出的 duration 字段,自己只负责派生 Hour/Month/Weekday/Daytime Indicator 等周边时间变量。

**改动规模**：中等偏大,不是"改一个聚合函数"的小改动（因为需要新增对 Re-interruption Stage 字段的读取和一套全新的聚合规则,目前完全没有这部分逻辑）,但也不是"整个数据读取结构都要重写"的大改动（改动范围局限在 `filter.py` 的 dedup 步骤之前插入新聚合逻辑,加上 `data_arrange.py` 的 duration 计算简化,其余全部 361 列下游特征计算逻辑不受影响）。详见 `04_与官方公式差异定位.md` 的完整分析。

**customers=0 的特殊情况**：Step 5 已确认无任何脚本对 customers=0 做特殊处理,当前的 0 值是原始数据自然带出的,重新聚合后这些记录的 customers 值可能发生变化（如果被丢弃的其他阶段记录中有非零客户数）,建议重算完成后重新统计 customers=0 的记录数量和具体 incident 列表,与当前版本对比。
